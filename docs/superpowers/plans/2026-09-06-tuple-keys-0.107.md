# 0.107.0 — tuple dict/set keys and `d[i, j]` subscripts

## The gap

Dict keys and set elements were restricted to `int` and `str`. That is the
restriction a transition table, a sparse grid and a two-argument memo all run
into immediately, so the workaround — flattening the parts into a string by
hand — showed up in every realistic program that needed a composite key. It
was found that way: `statemap.py`, a state machine keyed by
`(state, event)`, was rejected outright.

```
dict keys/elements of type tuple[str, str] are not supported yet
(only int and str)
```

The related `a[i, j]` syntax was rejected in the *parser*, since 0.87, with a
diagnostic that named this same restriction as its reason.

## What was actually missing

Only hashing. `slot_eq` already compared `TAG_TUPLE` slots structurally through
`pyrs_tuple_eq`, so two equal tuples already compared equal in a dict; there was
simply no way to reach the right bucket. `hash_key` handled `TAG_INT` and
`TAG_STR` and died on anything else.

The GC needed nothing: `pyrs_gc_trace_object` visits dict and set key slots
already, and `gc_visit_slot` is conservative, so a tuple reachable only as a key
stays alive. This was verified under collection pressure rather than assumed.

## The contract

- `int`, `str`, and tuples whose elements are themselves hashable, nested
  arbitrarily, are valid dict keys and set elements — in literals, subscripts,
  `in`, `get`/`pop`/`setdefault`, `del`, iteration, `dict()`, and dict/set
  comprehensions.
- `d[i, j]` is `d[(i, j)]`, including a trailing comma for a 1-tuple
  (`d[3,]`). A tuple subscript of a list is now a *type* error, which is what
  CPython raises too, rather than a parse error.
- `bool` stays rejected. It hashes fine, but CPython's `True == 1` means a bool
  key would have to collide with an int one, and this subset does not model
  that. Rejecting is honest; silently disagreeing would not be.
- `float` and every other unhashable type stay rejected, now with a message
  that names what *is* allowed: `int, str, or a tuple of those`.

## Implementation

| Site | Change |
|---|---|
| `codegen/runtime/runtime.c` `hash_key` | new `TAG_TUPLE` arm calling `hash_tuple_key`, which folds element hashes with FNV-1a and recurses through `hash_key`, so nested tuples and unhashable elements both fall out of the existing dispatch. `TAG_BOOL` hashes as its int. |
| `semantic/src/lib.rs` `check_hashable_key` | rewritten around a new `is_hashable_key_ty`, which accepts int, str, and non-empty tuples of hashable types. |
| `semantic/src/lib.rs` — three more gates | `dict()` from pairs, set comprehensions and dict comprehensions each had their own hardcoded `Int | Str` match; all three now call `is_hashable_key_ty`. |
| `parser/src/lib.rs` | the `a[i, j]` rejection becomes a `TupleLit` subscript; a trailing comma is allowed. |

The hash is internal and never observed, so any mix that agrees with the
existing equality works — there is no CPython hash value to match.

`cli/tests/tuple_keys.rs` is the differential suite: literals, value (not
identity) equality, overwrite, order sensitivity, arities 1–3, nesting,
`get`/`pop`/`del`, iteration, sets, both comprehension forms, all three
subscript spellings, a transition table, a two-argument memo, a
collection-pressure run, and the two rejections. Every case runs against
CPython at `-O0/-O2/-O3`.

`cli/tests/annotation_syntax.rs` had a test pinned to the old parse-level
rejection; it now asserts the type error, which is the honest replacement.

## Out of scope

`frozenset` and `float` keys; a general `__hash__` protocol for user classes;
dict views. Separately found and *not* part of this milestone: `str()` and
f-strings cannot stringify any container (`str((1, 2))`, `f"{[1, 2]}"`), even
though `print` formats them — recorded as a gap.
