# A dynamic value is a register pair

**Status: implemented in 0.142.0.** Tier 1 of
[the dynamism plan](2026-09-10-dynamism-at-native-speed.md), whose D1 this
closes. The research that chose it is in
[the type-prediction study](2026-09-10-type-prediction-research.md).

## Why this was first

The obvious way to make dynamic Python fast is to work out its types. The
measurement said otherwise.

Three versions of one 20M-iteration loop, at -O2:

| Version | Time | Allocated | vs CPython |
|---|---:|---:|---:|
| `i: int` — fully typed | 0.0226s | 0 B | 37.1× |
| `v: int \| str = i` | 0.0227s | 0 B | 36.9× |
| `v: int \| str \| float \| bool \| None = i` | 0.0229s | 0 B | 36.6× |
| `v: object = i` — **before** | 0.6539s | **320 MB / 305 GCs** | 1.3× |
| `v: object = i` — **after** | **0.0227s** | **0 B** | **36.9×** |

A union is free, and **union width is free** — five members cost what one
does. `Ty::Union` lowers to an LLVM `{ i32, i64 }` living in two registers;
`Ty::Any` lowered to an `i64` pointing at a GC box `PyrsUnionBox { i32
print_tag; i64 payload }` holding *the same two fields*.

The emitted IR settled it. The `object` loop and the five-member-union loop
were identical except for one instruction:

```
call ptr @pyrs_union_box_new(i32 %tag, i64 %payload)
```

**One call was the entire 28.6× gap.** No amount of type prediction removes
it: a correctly predicted type stored into a boxed representation still
allocates. The literature agrees from the other direction — the only
published study that fed predicted types to an AOT compiler reports 1.0×,
*no speedup at all*, on the kernel where its predictions missed.

So the fast dynamic representation already existed in the tree, fully
implemented and already correct. `Any` simply did not use it.

## The change

`Ty::Any` now lowers to `{ i32, i64 }`.

The insight that made it small: **`Any` is the open union.** A closed union's
pair carries a *member index* into its type list; `Any`'s carries a *print
tag*. Same layout, same two registers, same GC treatment — and the tag spaces
already agreed, because `elem_tag` had always mapped both to 8.

The box survives at exactly two boundaries, and both were already boxing
unions for the same reason:

| Boundary | Why a box is still needed |
|---|---|
| A container slot | `PyrsList` is `{ len, cap, data }` with 8-byte slots and no per-element tag |
| The C runtime ABI | `pyrs_print_any(long long)` and friends take one word |

Everything else — locals, parameters, returns, class fields, module globals,
closure captures, generator frames — is now inline.

Sites changed, all in `codegen/src/emit.rs`:

- `lty` — `Ty::Any` joins `Ty::Union` at `{ i32, i64 }`
- `slot_from_value` / `value_from_slot` — the two container boundaries, now
  `any_box` / `any_unbox`
- `emit_to_any` — builds the pair with `insertvalue`; no allocation
- `emit_any_unpack` — two `extractvalue`s, where it used to load from a box;
  the box-reading version survives as `emit_boxed_any_unpack` for the
  container path
- every C-ABI call site — boxes its argument, unboxes an `Any` result
- `gc_root_range_size`, the three zero-initialisers, and `emit_is_identity`

Roughly fifty lines. The blast radius the plan feared — `lty(Ty::Any) == i64`
assumed across ~20k lines of lowering — did not materialise, because the
lowering deals in `Ty` and the representation lives in six functions.

## Two things no test would have found

Both came from an adversarial review of the diff, not from running it.

### A dynamic global is 16 bytes

`gc_root_range_size` returned `Some(8)` for `Ty::Any`, correct when the slot
held a single pointer. An inline pair is 16, and the collector must be told
so: **the payload word can be the only live reference to an object.**
Registering 8 would have traced the tag and ignored the pointer beside it —
an intermittent, load-dependent collection bug, the worst kind to find later.
The existing unit test caught this one, which is why that test was written the
way it was.

### An unwritten dynamic slot must say None

This one segfaulted, and nothing in the suite noticed.

`zeroinitializer` is `{ 0, 0 }`. Tag 0 is `int` — and payload 0 is **not** a
tagged small integer, because tagging sets the low bit, so small zero is `1`.
The runtime therefore read payload 0 as a heap `PyrsInt*` and dereferenced
address 0.

The old representation had no such hole: a zero `i64` was a null box, and
`emit_boxed_any_unpack` mapped null to tag -1, None. LLVM cannot spell tag -1
with `zeroinitializer`, so the initialiser now names it:

```rust
const ANY_NONE_INIT: &str = "{ i32 -1, i64 0 }";
```

A union can keep `zeroinitializer` because member index 0 is a real member.
The open union has no member 0 to fall back on.

Where it fired matters. Locals were safe — every `Local` read goes through
`emit_binding_check`, and an unassigned dynamic local still raises
`UnboundLocalError`. But **`GetField` and `GlobalLoad` carry no such check**:

```python
class Box:
    def __init__(self, flag: bool) -> None:
        if flag:
            self.x: object = "hello"
Box(False).show()      # exit 139 before the fix
```

```python
if False:
    x: object = "hello"
print(x)               # exit 139 before the fix
```

Both now read `None`, which is what the old representation produced. That is
parity with the previous behaviour, **not** with CPython, which raises
`AttributeError` / `NameError` here. That divergence predates this work.

## One semantic change, currently unreachable

`x is y` on two dynamic values compared box *addresses*; it now compares tag
and payload, exactly as a union already does. Semantic rejects `is` on `Any`
(`'is' / 'is not' is not supported for type Any`), so nothing reaches it
today.

If it is ever opened up, the choice needs making deliberately rather than
inheriting this one. Payload equality is **closer** to CPython for `None`,
interned small ints and the same heap object; it is **further** for floats
(the payload is the double's bits, so `1.0 is 1.0` would be true) and for
ints outside CPython's interning range (`1000 is 1000` would be true).

## Verification

- `make ci` — fmt, clippy `-D warnings`, **1,783 tests**, hygiene, 15 examples
  byte-identical to CPython, compatibility at 81 native / 28 compat
- `cli/tests/dynamic_representation.rs` — 13 tests. Three assert the emitted
  IR directly (no box for a local, a global registered at 16 bytes, a box at
  a container slot). The rest run both engines at -O0/-O2/-O3 **and** under
  `PYRS_GC_STRESS=1`, because the payload word can be the only live reference,
  so collection pressure is the real gate. They cover None-in-`Any`, container
  round-trips, generator suspension, closure capture, parameters and returns,
  `isinstance` narrowing, and the two crash shapes above.
- Two failures found while testing turned out to be **pre-existing**, byte
  identical before the change (generator yield-type inference rejects a `str`
  yield it inferred as `int`). Confirmed by stashing the change and re-running
  rather than by assuming.

## What this does not do

*(Closed in 0.143.0 for operators; see
[the operator kernel](2026-09-10-dynamic-operators.md).)*

Reading a dynamic value is now free. **Operating on one is still refused at
compile time** — `a + b`, `a < b`, `a == b`, `-a` and `a.upper()` on an `Any`
are all compile errors. That is the next tier, D2: a generic kernel, so those
become a performance question instead of a possibility question.

What already works without narrowing: `print`, `bool`, `str`, `repr`, `len`,
`in`, f-string interpolation, indexing, iteration, `.keys()`, and `isinstance`
narrowing to a single non-container type.
